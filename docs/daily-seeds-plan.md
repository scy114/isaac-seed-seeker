# 每日爽种 / 每日毒种计划书

- 状态：产品需求已对齐，评分标准待补充
- 目标版本：The Binding of Isaac: Repentance+ `v1.9.7.17.J460`
- Profile：普通伊甸，全解锁
- 产品形态：离线单 EXE、本地 WebUI

## 1. 产品目标

“每日爽种 / 每日毒种”是一组可直接复制进游戏的伊甸开局盲盒。

每天为“爽种”和“毒种”各准备一个全体玩家一致的首选种子。玩家不想游玩首选时，可以继续随机更换同类别种子。页面默认只展示种子，不提前公开道具、属性、血量、资源或评分；只有玩家主动选择“揭晓开局（剧透）”后，才进入已有的种子解析流程。

该功能只评价伊甸出生瞬间已经确定的内容：

- 主动道具；
- 被动道具；
- 饰品、卡牌或胶囊；
- 基础随机属性；
- 初始红心、魂心；
- 初始硬币、钥匙、炸弹。

宝箱房、Boss 房、商店、恶魔房、地图布局和后续掉落不进入评分，也不出现在产品文案中。

## 2. 玩家体验

新增独立页面 `daily-seeds.html`，主页只保留一个入口。页面同时展示两个盲盒：

```text
                 今日伊甸开局
          2026-08-06 · J460 · 全解锁

      每日爽种                    每日毒种

       ABCD EFGH                  WXYZ 1234

   [复制种子] [换一个]        [复制种子] [换一个]
   [揭晓开局（剧透）]         [揭晓开局（剧透）]
```

默认页面不显示分数、道具图标、道具名称、属性或入选原因。“爽种”和“毒种”本身是唯一的强弱提示。

### 2.1 今日首选

- 同一日期、Profile 和评分规则版本下，所有玩家看到相同的爽种首选和毒种首选。
- 爽种首选从当日合格候选中按分数加权抽取；高分更容易出现，但不会由单一道具长期垄断。
- 爽种抽取随机源由日期键决定，因此同一天的公共首选保持一致。毒种的首选策略在毒种评分完成后单独确定。
- 页面提供“回到今日首选”，玩家更换种子后仍可找回当天公共种子。

### 2.2 换一个

- “换一个”只从当天同类别的合格候选池抽取。
- 更换后的结果属于玩家本次程序会话，不要求不同玩家获得相同顺序。
- 随机抽取使用 Windows 系统随机源，不由前端时间戳或 `Math.random()` 决定。
- 已经展示过的种子在本次会话内不重复，今日首选也不会再次抽到。
- 爽种池和毒种池分别维护抽取状态，互不影响。
- 候选池用完后停止抽取并提示“今天的候选已经看完”，由玩家选择回到首选或重新洗牌。
- 重启程序后回到当天公共首选；随机抽取历史不需要跨进程保存。

### 2.3 主动揭晓

- 日常页面不会预先请求完整开局数据。
- 玩家点击“揭晓开局（剧透）”后，跳转到种子解析页并显式解析该种子。
- 复制种子和更换种子不会触发解析。
- 不增加自动展开、悬停预览或评分提示，避免误剧透。

## 3. 每日候选生成

完整遍历 `2^32` 个内部种子不适合作为每次打开页面的默认动作。每日功能采用固定规模的确定性分片：

```text
北京时间日期 + Profile ID + DailyRulesVersion
                    ↓
            生成起点和奇数步长
                    ↓
         无重复遍历当日候选分片
                    ↓
        伊甸开局预测 + 加权评分
                    ↓
       爽种 Top-K / 毒种 Bottom-K
                    ↓
       固定首选 + 会话内随机候选池
```

### 3.1 日期键

- 日期固定采用北京时间（UTC+8），每天 `00:00` 更新。
- 日期键格式为 `YYYY-MM-DD`，计算时不依赖系统本地时区。
- 哈希输入必须包含 Profile ID 和评分规则版本；不同规则生成的结果不会共用缓存。

### 3.2 候选序列

- 日期键经过稳定的 64 位哈希得到当日起点和步长。
- 步长强制为奇数，使其在 32 位种子空间中构成无重复排列。
- 扫描前 `N` 个候选；`N` 由性能基准测试决定，不在设计阶段凭感觉写死。
- 并行扫描沿用现有 C++20 内核和每线程有界排名结构。
- 全局合并使用固定排序键，保证线程数变化不改变首选和候选池内容。

### 3.3 候选池

- 爽种池保存当日最高分的一组种子，毒种池保存最低分的一组种子。
- 池大小应足以支持多次更换，同时避免把接近普通水平的种子混入“爽种”或“毒种”。
- 除 Top-K / Bottom-K 外，再执行类别门槛；未达到爽种或毒种门槛的种子不能只因排名靠前而入池。
- 当日有效候选不足时缩小池，不降低门槛凑数。

初始基准建议测试以下组合，再决定发行默认值：

| 扫描数量 | 单类候选池 | 需要记录的指标 |
| ---: | ---: | --- |
| 10,000,000 | 32 | 总耗时、候选分布、极值稳定性 |
| 50,000,000 | 64 | 总耗时、候选分布、极值稳定性 |
| 100,000,000 | 128 | 总耗时、候选分布、极值稳定性 |

`daily-good-v0` 首轮基准最终采用每日 `10,000,000` 个候选：本机发行构建单日约 `0.125` 秒，平均产生约 `90,800` 个合格爽种。该规模已足够支持稳定的带权抽取，继续扩大扫描量对首轮校准没有实际收益。

## 4. 评分系统

评分采用加权模型，但具体权重、门槛和特殊条目由玩家经验驱动，不在本计划书中预设结论。

评分输入只来自现有 `EdenStart`：

```text
DailyScore =
    主动道具分量
  + 被动道具分量
  + 口袋物分量
  + 基础属性分量
  + 血量分量
  + 初始资源分量
  + 少量明确的组合修正
```

### 4.1 评分原则

- 道具品质可以成为基础权重，但不能替代玩家评价。
- 属性按其真实可出现区间归一化后加权，避免不同单位直接相加。
- 基础属性和道具效果保持分离；首版不建立通用道具结算引擎。
- 只为明确、稳定、对开局影响显著的道具增加人工修正。
- 组合修正保持少量且可解释，不尝试穷举所有协同。
- 爽种和毒种允许使用不同门槛，不能简单把同一个总分乘以 `-1`。
- 评分仅供选种，不在默认页面向玩家展示。

### 4.2 确定性

- 排名使用整数定点分数，避免不同编译器或平台的浮点舍入改变顺序。
- 每个分量保留独立整数明细，便于测试和调权。
- 评分规则具有显式版本号，例如 `daily-v1`。
- 修改权重、门槛、人工修正或归一化公式时必须提升规则版本。

### 4.3 待补充的玩家标准

实施前需要形成一份可测试的评分表，至少包含：

- 主动道具基础分与极端修正；
- 被动道具基础分与极端修正；
- 饰品、卡牌、胶囊的分类评价；
- 六项随机属性的权重和上下限倾向；
- 红心、魂心、硬币、钥匙、炸弹的权重；
- 爽种硬门槛；
- 毒种硬门槛；
- 明确需要奖励或惩罚的少量组合。

评分标准确定后，先用人工挑选的正反例种子做排序测试，再进入每日扫描实现。

### 4.4 已确认：爽种 `daily-good-v0`

首轮爽种校准采用“硬门槛 + 少量连续权重”，不逐个评价全部 Q3 道具。

硬门槛：

```text
主动道具品质 >= 3
被动道具品质 >= 3
被动道具 != C149 吐根酊
移速 >= 1.00
射速 >= 3.00
伤害 >= 3.00
```

`C550`、`C551`、`C552` 在 J460 全解锁 Profile 中已经标记为伊甸不可用，不写入业务排除表，只保留数据正确性测试。

通过门槛的种子获得基础抽签权重 `100`，再增加以下整数权重：

| 分量 | 首轮权重 |
| --- | ---: |
| 主动道具为 Q4 | `+40` |
| 被动道具为 Q4 | `+40` |
| 主动道具为 C628 死亡证明 | `+30` |
| 伤害 `3.00 -> 4.50` | 线性 `0 -> 30` |
| 射速 `3.00 -> 3.501433905` | 线性 `0 -> 30` |
| 移速 `1.00 -> 1.15` | 线性 `0 -> 15` |

总权重范围为 `100–285`。Q3 只负责通过门槛，不维护逐道具手写评分。死亡证明拥有显著优势，但其权重有上限；每日公共首选采用日期驱动的确定性带权抽取，而不是直接取最高分。

这组数字属于校准起点，不直接视为稳定规则。先生成一批跨日期样本，统计死亡证明和其他高品质道具的出现频率，再根据人工“爽 / 一般 / 不爽”判断调整。规则通过人工验收后提升为 `daily-good-v1`。

### 4.5 人工 Q3 评分：`daily-good-v1`

`daily-good-v1` 使用完整 J460 伊甸池中的 183 个 Q3 道具人工评分，其中主动 27 个、被动 156 个。评分数据保存在 `data/daily-good/q3-ratings.j460.json`，并由 `scripts/generate-daily-q3-ratings.py` 生成编译期查询表；测试会检查资料表覆盖率和生成结果是否同步。

评分分布为：1 档 17 个、2 档 83 个、3 档 52 个、4 档 31 个。当前奖励映射如下：

- 1 档：`+0`
- 2 档：`+15`
- 3 档：`+30`
- 4 档：`+50`
- 普通 Q4：维持 `+40`
- 死亡证明：在 Q4 奖励外继续额外 `+30`

相同的 100 天、每日 1000 万候选基准中，v1 平均选择权重由 v0 的 `159.1` 提升至 `189.2`，Q3 人工评分平均贡献 `33.9`。品质组合仍保持多样：62 次 Q3/Q3、7 次 Q3/Q4、27 次 Q4/Q3、4 次 Q4/Q4；没有退化为只推荐双 Q4。

## 5. 后端设计

新增独立的 `DailySeedSession`，复用现有伊甸预测内核，不把每日状态塞入通用 `SearchSession`。

建议数据结构：

```text
DailySeedKey
  date_utc8
  profile_id
  rules_version

DailyCandidate
  seed_u32
  category
  score_total
  score_components

DailySeedPool
  primary
  candidates
  remaining_indices

DailySeedSession
  key
  good_pool
  bad_pool
  generation_status
```

`DailyCandidate` 在后端保留评分明细用于测试和调试，但公共日常接口只返回种子和类别。

### 5.1 HTTP API

接口保持本地会话令牌校验：

#### `POST /api/v1/daily/start`

启动或复用当日候选生成任务。

```json
{
  "date": "2026-08-06"
}
```

#### `GET /api/v1/daily/status`

返回扫描进度。未完成时页面显示简单的生成状态，不展示候选详情。

#### `GET /api/v1/daily/seeds`

生成完成后返回两个公共首选：

```json
{
  "date": "2026-08-06",
  "profile": "J460-full-unlock",
  "rules_version": "daily-v1",
  "good": {"seed": "ABCD EFGH"},
  "bad": {"seed": "WXYZ 1234"}
}
```

响应不包含 `EdenStart`、分数或入选原因。

#### `POST /api/v1/daily/reroll`

```json
{
  "category": "good"
}
```

从对应会话候选池随机返回一个未展示过的种子。候选耗尽时返回明确状态，不自动降低评分门槛。

#### 现有 `POST /api/v1/inspect`

仅在玩家主动点击“揭晓开局（剧透）”后调用，不为每日功能增加第二套解析器。

### 5.2 缓存

每日候选生成可能比普通页面启动更耗时，因此增加版本化磁盘缓存：

```text
%LOCALAPPDATA%\IsaacSeedSeeker\cache\daily\
  J460-full-unlock_daily-v1_2026-08-06.json
```

- 缓存保存首选、候选池、分数明细、扫描规模和校验信息。
- 缓存键必须同时匹配日期、Profile、规则版本和程序数据版本。
- 缓存损坏或版本不匹配时重新计算，不尝试兼容旧评分结果。
- 随机抽取历史不写入缓存。
- 发布包仍为单 EXE，不引入 Python、Node 或数据库运行时。

## 6. 前端设计

### 6.1 主页入口

- 主页增加一个“每日伊甸开局”入口，不直接摆放两组完整结果。
- 入口与“实验性疗法”“种子解析”保持同一视觉体系。
- 主页不自动启动每日扫描。

### 6.2 日常页面

- 爽种与毒种使用两张独立纸片，种子按 `4 + 4` 显示。
- 复制后提供短暂状态反馈，不改变纸片内容。
- “换一个”按钮说明其类别，不把爽种池和毒种池混用。
- 页面显示日期、Profile 和规则版本，但不显示分数。
- 生成过程中展示扫描进度和预计候选数量；不使用虚假的循环动画冒充进度。

### 6.3 剧透入口

- “揭晓开局（剧透）”视觉级别低于“复制种子”和“换一个”。
- 点击后跳转到现有种子解析页，并以用户主动操作作为揭晓边界。
- 返回日常页面时保留本次会话中的当前种子和已抽取集合。

## 7. 验证方案

### 7.1 确定性测试

- 相同日期、Profile、规则版本和扫描规模得到相同候选池。
- 单线程和多线程得到相同首选、相同排名和相同平分处理结果。
- 修改时区环境变量不改变北京时间日期键。
- 修改规则版本后不会读取旧缓存。

### 7.2 评分测试

- 每个评分分量独立覆盖最低值、基准值和最高值。
- 人工指定的爽种正例必须排在普通种子之前。
- 人工指定的毒种正例必须排在普通种子之后。
- 所有硬门槛均有通过和拒绝测试。
- 评分表每次修改都输出固定样本的排名差异，供人工复核。

### 7.3 随机更换测试

- 第一次显示始终是公共首选。
- 会话内随机更换不重复。
- 爽种更换结果全部来自爽种池，毒种同理。
- 候选池耗尽后不越界、不跨类别、不静默重复。
- 回到今日首选不会改变剩余候选池。

### 7.4 防剧透测试

- 日常页面初次加载不调用 `/api/v1/inspect`。
- 复制和更换操作不请求完整开局数据。
- 只有点击“揭晓开局（剧透）”才进入解析流程。
- 日常公共接口响应不包含道具 ID、属性、血量、资源或评分。

### 7.5 性能测试

- 在发行构建中测量 1000 万、5000 万、1 亿候选的耗时和峰值内存。
- 对比不同线程数的吞吐量与确定性。
- 记录首次生成和缓存命中的页面等待时间。
- 默认扫描规模以真实测试结果决定，并在 UI 中报告真实进度。

## 8. 实施阶段

### 阶段 A：评分标准与样本

1. 记录玩家提供的权重、门槛和特殊修正。
2. 将标准转换为版本化评分配置和整数定点公式。
3. 准备人工确认的爽种、普通种、毒种样本。
4. 用排序报告验证评分是否符合实际游玩判断。

完成条件：固定样本的排序得到玩家认可。

### 阶段 B：每日生成内核

1. 实现日期键、确定性候选序列和规则版本。
2. 实现爽种 Top-K、毒种 Bottom-K 和硬门槛。
3. 实现 `DailySeedSession`、随机无重复抽取和缓存。
4. 完成确定性、缓存、随机和性能测试。

完成条件：同一构建在不同线程设置下得到相同公共首选。

### 阶段 C：本地 API 与盲盒页面

1. 增加每日任务与进度接口。
2. 制作独立日常页面和主页入口。
3. 接入复制、换一个、回到首选。
4. 接入主动揭晓，并复用种子解析页。

完成条件：默认页面和接口都不泄露开局详情，玩家可以完整完成盲玩流程。

### 阶段 D：实机验收

1. 选取多个日期生成爽种和毒种候选池。
2. 在游戏内抽查首选及若干随机更换结果。
3. 根据实际游玩感受调整评分，不用单个异常样本修改 RNG 内核。
4. 固定 `daily-v1` 后再制作朋友测试版。

完成条件：评分表现、生成速度和盲盒体验均通过人工验收。

## 9. 首版完成定义

- 每天北京时间零点产生新的公共爽种首选和毒种首选。
- 相同版本和 Profile 的玩家获得相同公共首选。
- 玩家可以在两个合格候选池内随机更换，当前会话不重复。
- 默认页面和每日公共接口不公开开局详情与分数。
- 玩家可以主动跳转到现有解析页揭晓结果。
- 评分只使用伊甸出生瞬间的数据，不声称预测任何房间或后续掉落。
- 候选生成、排名和缓存具有版本化回归测试。
- Windows 发行物继续保持单 EXE、离线运行、无需额外运行时。

## 10. 开工前确认项

以下内容留待评分讨论后确定：

1. 主动、被动、口袋物、属性、血量、资源的具体权重。
2. 爽种和毒种的硬门槛。
3. 需要人工奖励或惩罚的道具与少量组合。
4. 毒种首选采用绝对最低分还是在低分区间中确定性抽取。
5. 性能测试后采用的扫描数量和候选池大小。
6. 候选池用完后是否允许重新洗牌，或只允许回到今日首选。

评分标准确定前，不进入内核实现。
